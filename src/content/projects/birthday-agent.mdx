## 01 · 问题

32 个人的生日，靠人记一定会漏。但「今天谁过生日」一旦发到班级群，祝福就变成了刷屏 —— 被祝福的人收到的是几十条一模一样的「生日快乐」。

所以真正的约束不是「怎么记得住」，而是**怎么在自动化的同时保住「这封信是写给我的」这个感觉**。

## 02 · 自动化

整条链路无人值守：

```
GitHub Actions（每天北京 08:00）
        ↓
读取名单 → 比对今天是谁的生日
        ↓
按「应发日期」选择文案版本（第一版 / 第二版）
        ↓
变量渲染 → 逐封单独投递（间隔 3 秒）
        ↓
写入已发记录（学号-年份），保证幂等
```

真实运行输出（学生姓名与学号已脱敏）：

```text
$ python src/birthday_mail.py check
== 体检 ==
  ✅ 名单完整：32 人，生日与邮箱齐全
  ✅ 模板加载正常
  ✅ 体检通过

$ python src/birthday_mail.py simulate --year 2027
== 2027 年全班生日日历 ==
  2027-01-02  ███（2026·······）→ 第一版
  2027-01-03  ███（2026·······）→ 第一版
  2027-01-12  ███（2026·······）→ 第一版
  2027-01-21  ███（2026·······）→ 第一版
  2027-02-03  ███（2026·······）→ 第一版
  （其余 27 条已省略）
共 32 人生日齐全。
```

## 03 · Workflow 设计

### 绝不群发，写进代码

- 每封邮件只有 **1 个收件人**，逐封单独投递，投递间隔 3 秒
- 主题行必须能在 `config/模板-主题.txt` 里原样找到，**禁止程序自由生成**
- 渲染后如果还残留任何 `{{变量}}`，直接抛错阻断 —— 绝不能把 `{{姓名}}` 原样发出去

### 名单只留月日，不留年份

名单里没有出生年份这一列。少一个字段，就少一类泄露风险，也少一点「被系统分析」的感觉。

渲染层甚至把 `{{年龄}}` 列为「出现即报错」的变量 —— 从代码层面保证没有人能把这封信变回一份数据报表。

### 失败是被考虑过的，不是被假设掉的

| 机制 | 解决的问题 |
| --- | --- |
| 补发窗口 3 天 | 某天没跑成功，之后 3 天内自动补发这期间的生日 |
| 幂等（学号-年份唯一） | 同一个人同一年只发一次，重跑不会重复投递 |
| 判定基准是「应发日期」而不是「运行日期」 | 补发时不会选错文案版本 |

### 文案和代码彻底分开

所有文案都在 `config/模板-*.txt` 里，下一届班委用记事本改、保存即生效，不用碰代码。

一个只服务 32 个人的工具，不应该要求使用者会写程序。

## 04 · 关于 AI

**这个项目没有使用 AI 生成文案，这是刻意的判断，不是能力缺失。**

我试过让模型生成祝福。问题在于：32 个同学里，有人只想要一句朴素的生日快乐，有人喜欢被调侃两句。模型生成的文案在统计上是「平均好看」的，但**「平均好看」恰恰意味着不会出错、也不会被记住**。

而这件事的核心体验是「这封信是专门写给我的」。手写的两版文案 + 精确的变量渲染（姓名 / 班级 / 季节 / 年份），比一个每次都略微不同的模型输出更稳定地交付这个感受。

这里的取舍是：**在「个性化」和「可靠」之间，这个场景应该选可靠。**

> 该用 AI 的地方是「识别」和「生成」，不是「替代情感表达」。
> 判断要不要用模型，不看这个任务难不难，而看**失败一次的代价**，以及**稳定性本身是不是需求的一部分**。

## 05 · 实现

7 个 Python 模块，职责拆开：配置加载、名单读取、文案渲染、排期与补发、SMTP 发送、已发记录持久化，加一个主入口。

CLI 提供 5 个子命令，其中两个是给自己兜底用的：

| 命令 | 用途 |
| --- | --- |
| `check` | 体检：配置 / 名单 / 模板是否有问题 |
| `preview` | 预览某个同学的邮件（两版文案都能看） |
| `simulate` | 模拟整年日历，确认排期没有漏 |
| `plan` | 生成待发清单，不发送 |
| `send` | 真实投递 |

**零第三方依赖** —— 全部使用 Python 标准库，这让它在 GitHub Actions 上的冷启动非常快，也不会因为依赖升级而失效。

密码/授权码不落盘，从环境变量 `SMTP_PASSWORD` 读取；含全班邮箱的名单文件不进入公开仓库。
