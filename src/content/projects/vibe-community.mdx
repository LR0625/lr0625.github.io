maturity: concept

problem: AI 让「做出一个东西」变容易了，但做出之后呢？作品散落在聊天记录、本地文件、临时链接里。作者不知道给谁用，想用的人拿不到、也不会部署。生成的门槛塌了，分发的门槛还在。

insight: 所有人都在优化「生成」，没有人认真做「生成之后」。Vibe Coding 创作者最缺的不是更强的模型，是一个能把作品接住、并且让非专业用户也能用上的地方 —— 断点已经从「做不出来」转移到了「做出来了，然后呢」。

proposal: 一个低门槛 AI 应用分发商店。核心链路是「作品上传 → 自动处理 → 发布 → 一键获取/使用」，把部署这件事从作者身上拿走，让使用者的操作收敛到一次点击。围绕这条链路长出创作者循环、社区机制与内容安全治理。

nonGoals:
  - 不做通用代码托管 —— 那是 GitHub 的位置，重复造它没有意义
  - 不做模型能力比拼 —— 那是模型厂商的位置
  - 不做全品类覆盖 —— 先只做大学生创作者，宁可窄

statusNote: 方案阶段，未开发。已完成产品定位、核心链路、创作者循环与内容安全治理的框架设计，没有可用实现，也没有真实用户。

## 02 · 用户问题：两侧卡在不同的地方

| 角色 | 卡在哪 | 现有方案为什么没用 |
| --- | --- | --- |
| 作者 | 不知道怎么让别人方便地用上。发个链接，对方打开是一堆代码 | GitHub 面向开发者，不解决「给非技术的人用」 |
| 使用者 | 拿到一个项目文件夹，不知道从哪开始 | 应用商店只接受已上架的成品，不接受个人作品 |
| 双方 | 没有地方能证明「这个东西有人在用」 | 社交平台分发的是内容，不是可运行的东西 |

<Callout label="结论">

生成的门槛塌了，分发的门槛还在。而现有方案各自服务于另一个问题。

</Callout>

整条链路的靶心只有一个：**使用者的第一个动作必须是「点一下」，而不是「看懂这是什么」。**

## 04 · 平台思维：这是双边问题

只解决供给或只解决需求都不成立 —— 没有作品使用者不会来，没有使用者作者不会留。

| 侧 | 要解决的核心问题 | 关键设计 |
| --- | --- | --- |
| 供给侧 | 上传成本必须低于「发给朋友」的成本 | 零配置，不要求作者理解任何部署概念 |
| 需求侧 | 打开成本必须低于「问作者要」的成本 | 一次点击可用，不需要注册就能试 |
| 冷启动 | 两边都不能空着 | 从**大学生创作者**切入，而不是全体创作者 |

选大学生创作者的理由很具体：密度高、主题集中、彼此之间有真实需求。学习、课程、效率、社团、校园生活 —— 这些场景足够具体，比泛化的「所有创作者」更容易跑出第一批有效供给。

## 05 · Creator Economy：只做分发是不够的

一个没有反馈回来的分发层，作者用两次就走了。

<Flow compact>
  <FlowStep n="01" title="上传作品 → 获得使用者" />
  <FlowStep n="02" title="看到使用数据 → 收到具体反馈" tone="key" />
  <FlowStep n="03" title="迭代 → 再上传" />
</Flow>

三个要点让这个循环闭上：

- **反馈要具体。** 不是「点赞」，而是「在某台设备上打不开」「这个步骤看不懂」—— 能让作者直接动手改的信息。
- **迭代要留痕。** 版本变化对使用者可见，让「有人在维护」本身成为质量信号。
- **作者要有身份。** 作者主页聚合全部作品与迭代记录，否则创作者的积累无法沉淀，每次发布都从零开始。

内容形态也不局限于「完整应用」：**Skill / Agent / Workflow / Prompt / 用户案例**。一个调好的 Prompt 和一个完整应用同样值得被分发，只是需要不同的展示方式 —— 应用需要一个能打开的入口，Prompt 需要「用它之前 / 用它之后」的对比，Workflow 需要能把步骤画出来。社区机制围绕这条供给展开：推荐、分类、收藏、作者主页、作品数据。
