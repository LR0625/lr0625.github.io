## 观察

教师的工作时间有两个来源：

1. **手动打卡** —— 她点上班、点下班，于是有了一个时段
2. **课表** —— 学校导出的课程时间，导入后系统知道她哪个时段有课

问题出现在两边都有数据的日子：同一天，日历上显示 5 小时，周视图里算出来 7 小时。用户问哪个是对的。

## 假设

第一反应是去查代码，但查之前我先问了一个更前面的问题：**「一天工作了多久」这件事，我们定义过吗？**

答案是：没有。

打卡和课表是两条完全独立的数据流，各自的累加逻辑单独看都没错。但如果同一个人在同一时段既打了卡、又有课 —— 这两段时间在物理上是同一段时间，在数据上却是两条记录。两个数据源各自求和，必然重复计算。

**所以这不是 bug，是缺失的定义。**

## 怎么验证

把口径显式写出来：

```
当日工时 = 打卡时段 ∪ 课表时段     （重叠部分只算一次）
```

用集合并集而不是算术加法。

然后做一件比公式更重要的事：**把判定收敛成唯一函数。**

```
courseOccursOn(课程, 日期)   // 周视图、日历、日期明细、工时统计全部只调它
```

四个地方如果各自判断「这节课今天上不上」，代码上就永远存在不一致的可能。收敛成一个函数之后，两边不一致在结构上就不可能发生 —— 除非这个函数本身错了，而那时错的是一处。

## 结论

修完之后，日历和周视图自动对上了，因为它们是同一个函数算出来的。

这件事改变了我对「不一致」这类问题的处理顺序：

> **遇到两个数对不上，先问「这两个数有没有被定义过」，再问「哪个算错了」。**

大部分看起来像 bug 的问题，根因是口径没定义。直接去改代码，往往只是把其中一处调成和另一处一样 —— 碰巧对了，但没解决。

后来我把这个习惯带到了别的地方：在 FSAE 车队做高压安全回路时，第一步也是先把规则落成真值表 —— **先让每个状态都有明确定义的输出，再谈电路怎么画。** 方法是同一个。
